fgsea stands for fast Gene Set Enrichment Analysis.

GSEA (Gene Set Enrichment Analysis) is the method, introduced by Subramanian et al. in 2005.
The “f” (fast) is because fgsea is a faster implementation of it, written as an R package by Korotkevich and colleagues. It’s reference 21 in the paper: “Fast gene set enrichment analysis.”

Speed matters because GSEA measures significance by shuffling the data many times to see what scores you’d get by chance. The original GSEA software did this slowly. fgsea uses a shortcut that reuses calculations between shuffles, which makes it practical to test many gene sets across several comparisons in seconds.

Two points for the report’s critique:
Ranking by raw log2FoldChange is a debatable choice. Genes with very few reads can show huge fold changes just by chance, and they’d land at the top or bottom of the ranking. A ranking that accounts for uncertainty (DESeq2’s stat column) is more common. We’ll follow the authors but note it.
The script is written for the human data. Line 54 points to the human gene set file, and the comments say to switch it for mouse. So the mouse run used an edited version that isn’t in the repo. A small documentation gap.

The genes at the very top and bottom are mostly near-zero-count genes (olfactory receptors like Olfr1110, pseudogenes, Gm genes) with absurd fold changes of ±15 to ±30. A fold change of 30 on a gene averaging 0.3 reads means, in practice, “a few reads in one group and none in the other.” Ranking by raw log2FoldChange puts these noise genes in the most influential positions for GSEA and pushes the real signals toward the middle. That explains why the directions are right but nothing is significant. And that’s a central point for the critique.

B. Sensitivity check: rank by DESeq2’s stat
stat is the fold change divided by its uncertainty, so near-zero genes with huge but unreliable fold changes get small values and drop toward the middle. Everything else stays identical to the authors’ setup (protein-coding only, the same gene sets, eps, minSize, maxSize, and seed). This test turned out to be inconclusive, because the filter removed nothing. All 20,068 protein-coding genes have a padj value, so the “filtered” run was identical to the authors’ run. The results match number for number.

Why: DESeq2’s independent filtering tries several low-count cutoffs and picks the one that gives the most discoveries. For our data, it picked no cutoff, so every gene was tested and none got padj = NA. You can see this in the diagnostic above: near-zero genes like Mmp27 (baseMean 0.35) and Olfr1331 had real padj values. I should have checked the number of NA padj values before suggesting this test. It would have shown in seconds that the filter wouldn’t do anything.

So the hypothesis, that the authors’ input table was filtered, is still untested, not ruled out.

Test filtering with a read-count cutoff: rank by log2FC, using only genes above a minimum baseMean. The catch is that any cutoff (e.g., 10) would be our choice, not something in the authors’ code or paper. We’d be guessing at what they might have done, so the result would be suggestive, not evidence.

run several cutoffs side by side. If the results change sharply between cutoffs, the filtering matters a lot. If they settle down above some level, that tells us something too.

The cutoffs below are my suggestion, not from the authors. 
baseMean ≥ 1: removes only genes that are essentially zero
≥ 5 and ≥ 10: common rule-of-thumb levels for “too few reads to trust”
≥ 20: a stricter level

Everything else is the authors’ setup (protein-coding, raw log2FC ranking, their gene sets, and settings), plus seed 6430:

cutoffs <- c(1, 5, 10, 20)

gsea_cut <- lapply(cutoffs, function(cut) {

What this tells us:
A simple read-count filter doesn’t explain the gap. Even with every gene under 20 reads removed, raw log2FC ranking stays weak. So the problem isn’t only near-zero genes. Fold changes for moderately expressed genes are still noisy enough to blur the pathways, and stat handles that because it accounts for each gene’s uncertainty.
The filtering hypothesis is now less likely, at least in this simple form. We still can’t rule out something else in their Supplemental Table S2 without seeing it.
Missing controls rises as an explanation. Fold changes measured against 3 PH controls (vs. their 5) are noisier, which hurts raw-log2FC ranking most. That’s exactly what C tests.

make_mats <- function(lst) {
  nes  <- sapply(lst, function(r) r$NES[match(fig1d, r$pathway)])
  padj <- sapply(lst, function(r) r$padj[match(fig1d, r$pathway)])

}

col_fun <- colorRamp2(c(-4, 0, 4), c("blue", "white", "red"))

draw_hm <- function(m, title, file) {
  ht <- Heatmap(m$nes, name = "NES", column_title = title, col = col_fun,
                column_names_rot = 45, cluster_rows = FALSE, cluster_columns = FALSE,
                row_names_gp = gpar(fontsize = 10), column_names_gp = gpar(fontsize = 10),
                cell_fun = function(j, i, x, y, w, h, fill) {
                  p <- m$padj[i, j]
                  if (p < 0.001)      grid.text("***", x, y, gp = gpar(fontsize = 10))
                  else if (p < 0.01)  grid.text("**",  x, y, gp = gpar(fontsize = 10))
                  else if (p < 0.05)  grid.text("*",   x, y, gp = gpar(fontsize = 10))
                })
  pdf(file)
  draw(ht)
  dev.off()
  draw(ht)
}

de_compare <- t(sapply(names(sheets), function(n) {

  theirs <- as.data.frame(read_excel(s2file, sheet = sheets[[n]]))

    theirs_genes     = nrow(theirs),
    shared_genes     = nrow(m),

    lfc_spearman     = round(cor(m$log2FoldChange.ours, m$log2FoldChange.theirs,

    ours_DEG         = sum(ours_deg, na.rm = TRUE),
    theirs_DEG       = sum(theirs_deg, na.rm = TRUE),
    DEG_overlap      = sum(ours_deg & theirs_deg, na.rm = TRUE),

Decisions for the mouse version.
Variable of interest: mod1 = ~ condition. It plays the same role as AGE in their human code: the biology SVA must not remove. And condition is what their mouse DESeq2 design uses.
Normalization: follow the code as written (log2 of raw counts). We’re reproducing what they actually ran, not what they may have meant. We’ll note the unused scaled matrix in the report.
Duplicated intercept: copy it exactly, for the same reason, and note it.
Seed: yes, set.seed(6430). It doesn’t change the method, and it lets the three of you get identical SV1 values. Same reasoning as for fgsea; we’ll document it as an addition.

Taken together: follow their code exactly wherever it exists, fill gaps with the closest analog from their own work, document every departure, and add only what makes results comparable across the group.
